# HCM Tasks Product Requirements Document

## 1. Product Summary

HCM Tasks is a lightweight, private task-management web application. Users create an account, organize tasks into Personal or Work lists, set priorities and due dates, track completion, and review their workload through focused views and summary metrics.

The product name shown in the interface is **HCM**. In this application, HCM is a brand name; the product is not a human-capital-management suite.

## 2. Goals

- Make capturing and updating a task quick on desktop and mobile.
- Give users clear ways to find tasks by status, due date, list, and search text.
- Preserve task data between sessions and isolate each account's data.
- Provide a focused interface that stays usable on narrow screens.

## 3. Non-goals

- Employee records, HR administration, payroll, recruitment, or leave management.
- Team sharing, collaboration, comments, or role-based organization management.
- Recurring tasks, notifications, calendar synchronization, attachments, or external OAuth sign-in.
- Cloud hosting or multi-tenant administration beyond per-user account isolation in the local app.

## 4. Users and Core Scenarios

### Primary user

An individual who wants a simple, persistent place to plan personal and work tasks.

### Core scenarios

1. Register or sign in to a private workspace.
2. Add a task with a title, optional notes, list, priority, and optional due date.
3. Review tasks due today, upcoming tasks, all tasks, or completed tasks.
4. Search tasks by title, notes, and list.
5. Edit task details, mark a task complete or incomplete, or delete a task.
6. Sort the visible task list by priority, due date, or creation time.
7. Sign out and return later to the same account's tasks.

## 5. Functional Requirements

### 5.1 Authentication and privacy

- The app must provide sign-in and account-registration views.
- Registration requires a name, a valid email address, and a password from 10 to 128 characters.
- Passwords are stored as salted scrypt hashes, never as plaintext.
- Successful authentication creates a server-side session represented by an opaque, HttpOnly, SameSite=Lax cookie with a 14-day lifetime.
- Task APIs require a valid session.
- Users may read, edit, and delete only their own tasks.
- Signing out invalidates the active session and returns the user to sign-in.

### 5.2 Task data

Each task contains:

- Numeric task ID.
- Required title, 1-160 characters.
- Optional notes, up to 1,000 characters.
- List: Personal or Work.
- Priority: Low, Medium, or High; default Medium.
- Optional due date. The form accepts a date; the server normalizes date-only values to local midnight with seconds (`YYYY-MM-DDT00:00:00`). Existing valid date-time values remain supported.
- Completion state, default incomplete.
- Creation and update timestamps generated by SQLite.
- Owning user ID.

### 5.3 Create and edit tasks

- A user can open the task dialog from the primary Add task actions.
- A task title is required. Notes and due date are optional.
- The dialog supports both creating and editing a task.
- The task form's action footer remains visible while its field area scrolls.
- Cancel and close actions dismiss the dialog without saving.
- Deleting a task requires confirmation.

### 5.4 Task views and search

- **All tasks** shows all tasks owned by the user.
- **Today** shows incomplete tasks whose due date is today.
- **Upcoming** shows incomplete tasks whose due date is after today.
- **Completed** shows completed tasks.
- List filters show tasks matching Personal or Work.
- Search matches task title, notes, and list name, case-insensitively.
- Summary counts and completion metrics reflect the user's task data.

### 5.5 Sorting

- A working sort control provides Priority, Due date, and Created at.
- Incomplete tasks appear before completed tasks.
- Priority order is High, Medium, then Low.
- Due-date order is earliest first, with tasks without a due date last.
- Created-at order is newest first.
- Stable secondary ordering uses creation time and task ID where applicable.

### 5.6 Created timestamp

- The app automatically records task creation time; users do not enter it.
- Desktop task rows show a Created at column.
- Mobile task rows show the created timestamp beneath the task title.

### 5.7 Responsive navigation and layout

- Desktop uses a persistent sidebar.
- Mobile uses a compact brand header and hamburger-triggered sidebar drawer.
- The mobile drawer closes after choosing a view/list and can be dismissed by close control, backdrop, or Escape.
- The task table adapts to mobile; Created time remains available beneath each task title.

## 6. UX and Accessibility Requirements

- Use semantic forms, labels, buttons, and headings.
- All controls must be keyboard reachable and have accessible names.
- Select2 is used for the Priority selector; List remains a native select.
- Dialog actions must remain reachable when content overflows.
- Focus should enter the task title on dialog open; native dialog behavior handles focus containment.
- Respect reduced-motion preferences.
- Use clear empty, loading/error, and signed-out states.

## 7. Data and Technical Constraints

- Browser UI: HTML, CSS, and TypeScript compiled to JavaScript.
- Server: TypeScript on Node.js with a small HTTP API.
- Persistence: SQLite using Node's `node:sqlite` API.
- Authentication uses scrypt, random session tokens, SHA-256 token hashes, and HttpOnly cookies.
- Runtime currently depends on Node.js with built-in SQLite support; SQLite is marked experimental by the runtime.
- No frontend framework or bundler is used. jQuery and Select2 assets are served locally.

## 8. Success Criteria

- A new user can register, create a task, sign out, and sign back in to find it.
- Anonymous requests cannot access task records.
- One account cannot access another account's tasks.
- Users can create, view, edit, complete, reopen, search, filter, sort, and delete tasks.
- Date-only inputs persist at midnight and display as readable local dates.
- The app builds successfully with `npm run build` and works at desktop and mobile widths.

## 9. Known Limitations / Future Considerations

- Account recovery, password reset, email verification, rate limiting, and OAuth are not implemented.
- There are no automated test or lint scripts yet.
- List choices are currently fixed to Personal and Work.
- Due dates are input as a date-only value; the persistence model accepts date-time values for compatibility, but the current product behavior is midnight local time.
- No deployment, backup, or database migration management workflow is provided.
